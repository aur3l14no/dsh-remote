# DSH Remote I/O 执行边界审查

## 为什么审查

DSH Remote 需要把工作区文件访问和进程执行分流到本次调用选定的 World，默认继承 Session 的绑定。但 DSH 及其插件原本有许多本机 I/O 实现：某个调用链如果直接使用 Node 文件系统、启动本机进程，或者间接调用包含这些操作的包装器，就可能绕过我们的 provider，在宿主上访问本应属于远端的路径或执行命令。

审查的目的是找出这些遗漏的 I/O 接点，尤其是新增消费者、调用链变化和上游升级引入的漏分流。不能仅检查 import，也不能把所有本机 I/O 都视为错误：配置、Session 历史、连接器和 SSH 传输等本来就有宿主职责。

采用两阶段流程：**CodeQL 用类似污点分析的数据流追踪找候选 → agent 读取候选链路及实际代码、装配，判断是否违反执行边界并报警。** SARIF 是第一阶段的输出，不是最终审查结论。

## 第一阶段：用 CodeQL 做初筛

### 扫什么、怎么产生候选

扫描对象包括本仓库的适配代码，以及 `integrations/dsh/patches/series.json` 指定、应用本项目补丁后的 DSH 上游。查询和扫描程序都在本 skill 中：

| 组成 | 工作 |
| --- | --- |
| [原生能力查询](codeql/queries/native-io-use.ql) | 从 Node `fs`、`fs/promises`、`child_process` 追踪别名、参数、返回值和属性传播，找到最终调用；补查没有明显工作区输入来源的 I/O |
| [工作区输入查询](codeql/queries/workspace-to-native-io.ql) | 把工具输入和 Session `header.cwd` 作为来源，通过污点传播寻找进入原生文件路径、命令、argv、cwd 的链路，优先暴露可能漏分流的接点 |
| [扫描脚本](scripts/scan.sh) | 从指定源码创建 JavaScript/TypeScript 数据库，执行上述查询，输出含 codeFlows 的 `results.sarif` |
| [上游准备脚本](scripts/prepare-upstream.mjs) | 检出固定上游，校验补丁 SHA-256 后应用，输出对应的 `series.json` |
| [回归校验](tests/check.mjs) | 根据 fixture 的正反例验证查询行为；不执行 fixture 中的 I/O |

工作区输入查询对已建模 API 只看决定目标的参数；对未建模原生调用允许任意实参成为候选。因此它可能把日志内容等非目标参数也报出来，留给第二阶段判断。

### 本地运行与 CI 的关系

新审查先明确目标源码和改动范围，再按 [运行说明](references/running.md) 执行：安装固定查询依赖 → 验证 fixture → 扫描本仓库 → 准备并扫描补丁后上游。单个目标的专项审查可以只扫描该目标，但结论需写清范围。

仓库 `.github/workflows/node-io.yml` 在 push、PR 或手动触发时，在 GitHub runner 上调用这套脚本和查询，完成同样的初筛。它上传 `fixtures/results.sarif`、`repository/results.sarif`、`upstream/results.sarif` 和 `series.json`，供第二阶段使用。**CI 目前只自动执行初筛和查询回归，不自动完成 agent 边界审查；绿色 job 不表示没有边界违规。** 分析过程或回归断言失败才使该 job 变红。

用户查看已有 CI 时，可以复用匹配提交的 artifact，下载方法见运行说明；这只是获取第一阶段输出的一种方式。没有匹配报告或需要审查未提交改动时，应运行相应扫描，不能用旧报告替代。

交给第二阶段的输入是：SARIF、对应源码、本仓库提交/本地改动状态、上游 revision 和补丁身份，以及可取得的扫描诊断。确认报告成功生成且目标完整；缺失或失败的部分明确记录。

## 第二阶段：由 agent 解读并对真实违规报警

执行本 skill 的 agent 负责完成这一阶段。不能止于下载报告、统计条目或让用户自己判断候选。

### 从候选追到实际行为

1. 优先读取 `dsh/workspace-to-native-io` 的 codeFlows，定位来源、传播链、原生调用和具体参数。确认输入究竟代表工作区目标，还是内容、元数据或测试数据。
2. 用 `dsh/native-io-use` 核对原生能力来源，补查新增/改变的产品调用。测试、构建脚本、宿主控制状态和工作区消费者按实际用途归组，再审查相关调用；数量本身不是风险。
3. 对照扫描版本的源码追完整调用链：World 在哪里解析，来自本次显式选择还是 Session 绑定；操作最终交给哪个 FS/subprocess provider；是否在缺失上下文时落回本机。准备目录存在或工作区 HEAD 相近都不足以证明源码身份一致。
4. 检查实际 preset/overlay、provider 注册和工具选择。对本机 guard、非空 provider 或未加载的调用者，需要给出代码和装配依据。共用函数有多条进入路径时，排除其中一个调用者不能排除其他路径。
5. 若做增量审查，结合前后报告及 Git diff，排除行号平移、重命名和重复链路造成的假增量。历史排除结论只能作为线索，不能作为永久白名单。

### 什么算违规

只有证据表明：**当前支持且实际可达的调用需要操作某个工作区 World，却绕过正确分流，到宿主或其他 World 执行 I/O**，才作为已确认的边界违规报警。例如远端工具输入经包装器进入宿主 `readFile`，或远端 cwd 交给宿主进程启动。

宿主配置、绑定存储、组件缓存、系统 SSH、授权的 skill 部署等操作，需验证路径来源和入口后排除。附件上传暂存还要核对绑定 owner、远端持久源与清理，不能在远端读取失败时用宿主副本兜底。未启用的本机插件可排除当前可达性，但不能宣称它已适配远端。

证据不足的候选列为待确认，并说明缺少哪个调用者、装配条件或实现；不要把它直接报成漏洞，也不要判为安全。有必要时做聚焦的复现或路由测试来完成判断。

### 如何交付

先给结论：是否确认边界违规、是否有尚未解决的候选。对每个真实问题给出代码位置、触发条件和完整链路、预期 World 与实际 I/O 位置、影响及修复建议；“报警”默认是在本次回复中明确指出问题，不自动发外部消息或创建 issue。

随后说明主要候选的排除依据、增量变化和实际审查范围。没有发现问题时也应提供支持这一判断的证据；未审完的目标不得包含在“通过”结论中。默认直接回复，不生成额外 Markdown 报告，除非用户要求保存。

## 能力边界与维护

这是两项自定义 JavaScript/TypeScript 路由查询，默认通用安全查询关闭，不分析 Rust helper。它们不能完整建模 Cordis 动态装配、guard、非空 provider 或逐次调用上下文；隐式相对路径、re-export、反射、外部 SDK 和跨数据库关系也可能漏报。零候选不是安全证明，建库成功也不证明所有源码/元数据均已提取，需要查看诊断与提取日志。

查询、依赖锁、fixture 和扫描辅助脚本在本 skill 内维护。运行和维护方法见 [运行说明](references/running.md)；仅在研究查询演变或历史实验时读 [历史评估](references/2026-09-11-evaluation.md)，不套用其中的旧数字和判断。静态分析输出放独立临时目录，不写入本地 `artifacts/`；数据库含源码，不上传。
